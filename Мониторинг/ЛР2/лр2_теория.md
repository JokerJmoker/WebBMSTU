### 1.2. Границы модели угроз

Внешняя сеть / Интернет

Источники вредоносного ПО, сетевых атак и управляющих соединений

Windows Server 2012 R2 — 10.74.16.1

AD DS · DNS · DHCP · RRAS · NAT · GPO · журналы событий

Windows 10 Pro — клиент домена

Пользователь · приложения · SMB · локальная защита · журналы

Схема отражает логические роли. Для фактической связности необходимо учитывать настройки интерфейсов VirtualBox, правила RRAS и межсетевых экранов.

В модели следует рассматривать четыре основных сценария:

1. Внешнее воздействие на доступные сетевые службы сервера.
2. Первоначальное заражение клиентского компьютера с последующим распространением в домене.
3. Компрометация доменной учётной записи с использованием разрешённых прав.
4. Злоупотребление административными полномочиями или отключение средств регистрации событий.

Отдельно следует учитывать угрозы, связанные с самой виртуальной средой: доступ к файлам виртуальных дисков, снимкам состояния, общим папкам VirtualBox и интерфейсам управления виртуальными машинами. Они находятся за пределами журналов гостевых ОС и требуют отдельного контроля.

Ниже переработаны разделы 2 и 3 с привязкой к существующим компонентам стенда Windows Server 2012 R2 и Windows 10 Pro, а также к перечню журналов, доступных в системе. В разделе 2 вместо общих формулировок указаны конкретные журналы и события, по которым можно искать признаки реализации угроз. В разделе 3 дополнительные источники событий сопоставлены с угрозами из модели.

Важное уточнение: наличие журнала в системе не означает, что он уже ведёт необходимую регистрацию. Для обнаружения событий могут потребоваться включение соответствующего канала, настройка расширенной политики аудита или дополнительные параметры службы. Для Windows Server 2012 R2 и Windows 10 также следует учитывать различия в доступности отдельных каналов.

## 2. Вредоносное ПО и способы воздействия на инфраструктуру
Главное изменение — унифицировать таблицы 2.2–2.4 по единой классификации угроз, чтобы одна и та же базовая угроза не описывалась по-разному в зависимости от узла, а специфические угрозы были привязаны к конкретным службам инфраструктуры.

Предлагаю разделить угрозы на две категории:

- Базовые угрозы — характерны и для контроллера домена Windows Server 2012 R2, и для клиента Windows 10. К ним относятся подбор паролей, использование похищенных учётных данных, повышение привилегий, закрепление в системе, запуск вредоносного кода и уничтожение следов.
- Специфические угрозы — связаны с определёнными ролями и компонентами. Для контроллера домена это AD DS и GPO, для сетевых служб — DNS, DHCP, RRAS, NAT и брандмауэр, для клиента — SMB, локальная защита и пользовательская среда.

При этом закрепление следует учитывать в обеих категориях: локальное закрепление относится к базовым угрозам, а закрепление через доменные учётные записи и групповые политики — к специфическим угрозам AD DS.

Ниже — переработанный вариант таблиц в формате Markdown для включения в теоретическую часть лабораторной работы.

Ниже три таблицы, приведённые к **согласованному** виду:

- **2.2** — только журналы, относящиеся к AD DS / доменным учётным записям / GPO. Ничего «сетевого» (DNS/DHCP/RRAS/NAT/firewall) здесь нет.
- **2.3** — только журналы, относящиеся к DNS / DHCP / RRAS / NAT / firewall. Ничего «доменного» (Directory Service, GroupPolicy, AD-учётки) здесь нет.
- **3.3** — **сборная** из 2.2 + 2.3 (плюс общие журналы, которые фигурируют в обеих: `Security`, `System`, `PowerShell/Operational`, `TaskScheduler/Operational`), сведённая в один перечень без дублей.

## 3. Настройка аудита Windows Server и Windows 10

### 3.1. Принципы выбора параметров

Настройка аудита должна обеспечивать регистрацию действий, соответствующих угрозам, определённым в разделе 2. Для этого используются следующие источники:

- базовая и расширенная политика аудита Windows;
- аудит доступа к объектам файловой системы, реестра и Active Directory;
- журналы системных компонентов и приложений;
- журналы Microsoft Defender и PowerShell;
- журналы DNS, DHCP, RRAS и NAT;
- журналы межсетевого экрана, сетевых соединений и SMB;
- журналы планировщика заданий и управления службами.

Для доменного стенда параметры безопасности целесообразно задавать централизованно через групповые политики. При этом необходимо проверять фактическое применение настроек на контроллере домена и клиентском компьютере.

Основной путь к расширенной политике аудита:

`Computer Configuration → Policies → Windows Settings → Security Settings → Advanced Audit Policy Configuration → System Audit Policies`

## 4. Методика оценки нагрузки аудита

### 4.1. Цель измерения и границы применимости

Необходимо сравнить три конфигурации:

- **A** — исходная: фактическая политика аудита до изменений;
- **C** — сбалансированная: регистрация критичных событий и необходимых для расследования действий при ограничении избыточного потока.

Моя методика измеряет **стоимость аудита** (объём данных, нагрузку на процессор, память и диск) и **покрытие заранее заданных тестовых сценариев**. Методика **не выполняет** верификацию модели угроз в полном объёме, поскольку эти самые угрозы не заданы по условию, одна без понимая, того, какими они могут быть, настроить сбалансированно аудит сложно (не понятно, от чего защищаться)

### 4.2. Фиксация исходного состояния системы

На первом этапе необходимо зафиксировать исходное состояние контроллера домена Windows Server и клиентской системы Windows 10 до изменения настроек аудита. С помощью `auditpol` сохраняется действующая конфигурация аудита, фиксируются перечень включённых журналов событий и их максимальные размеры. Дополнительно измеряются загрузка процессора, потребление оперативной памяти и объём свободного дискового пространства.

**Важно:** исходная конфигурация A — это **текущее** состояние системы, а не «ноль аудита». Часть журналов уже ведётся (`Security` — 6,3 МБ, `System` — 2,2 МБ, `Application` — 1,1 МБ) и создаёт фоновую нагрузку. Все приращения ΔU, ΔM и ΔS считаются относительно этого состояния, а не относительно полностью отключённого аудита.

Измеряемые параметры:

- $U_{исх}$ — исходная средняя загрузка процессора, %;
- $M_{исх}$ — исходный объём используемой оперативной памяти, Мбайт;
- $S_{своб,0}$ — исходный объём свободного дискового пространства, байт;
- $S_{жур,i}$ — максимальный размер $i$-го журнала событий, байт.

Средняя загрузка процессора:

$$
U_{исх}=\frac{1}{m}\sum_{i=1}^{m}u_i
$$

где $u_i$ — значение загрузки процессора при $i$-м измерении, %; $m$ — количество измерений.

### 4.3. Измерение фоновой активности

До выполнения тестовых действий необходимо в течение установленного интервала (10 минут) наблюдать за системой без целенаправленной тестовой нагрузки. За этот период регистрируются события, возникающие при обычной работе операционной системы, служб домена и сетевых компонентов.

**Назначение этапа.** Данные фонового интервала используются в дальнейшем для **вычитания вклада штатной работы** из результатов тестовых измерений. Без этого шага невозможно отделить стоимость аудита от стоимости обычной работы ОС.

Измеряемые параметры:

- $N_{фон}$ — количество зарегистрированных фоновых событий, шт.;
- $T_{фон}$ — продолжительность наблюдения, с;
- $V_{фон}$ — объём данных, сформированных журналами за период наблюдения, байт;
- $\lambda_{фон}$ — средняя интенсивность регистрации фоновых событий, событий/с;
- $R_{фон}$ — средняя скорость поступления фоновых данных, байт/с;
- $\bar{s}_{фон}$ — средний размер фоновой записи, байт/событие;
- $\Delta U_{фон}$ — изменение загрузки процессора за фоновый интервал, п.п.;
- $\Delta S_{фон}$ — изменение свободного места за фоновый интервал, байт.

Формулы:

$$
\lambda_{фон}=\frac{N_{фон}}{T_{фон}},\quad
R_{фон}=\frac{V_{фон}}{T_{фон}},\quad
\bar{s}_{фон}=\frac{V_{фон}}{N_{фон}}\ \ (N_{фон}>0)
$$

$$
\Delta U_{\text{фон}} = U_{\text{кон}} - U_{\text{нач}},\ \text{п.п.}
$$
$$
\Delta S_{\text{фон}} = S_{\text{нач}} - S_{\text{кон}},\ \text{байт}
$$
- $U_{\text{нач}}$ — загрузка процессора в начале фонового интервала, %;
- $U_{\text{кон}}$ — загрузка процессора в конце фонового интервала, %;
- $S_{\text{нач}}$ — свободное место на диске в начале фонового интервала, байт;
- $S_{\text{кон}}$ — свободное место на диске в конце фонового интервала, байт.

### 4.4. Измерение нагрузки при проведении эксперимента

Для каждой конфигурации аудита повторяется подготовленный набор тестовых действий. В течение измерительного интервала фиксируются количество зарегистрированных событий, объём сформированных данных, загрузка процессора, потребление оперативной памяти и изменение свободного дискового пространства.

### Подготовка одинаковой тестовой нагрузки

Для каждой исследуемой конфигурации выполняется одинаковый набор действий:

1. Успешный и неуспешный вход в систему.
2. Изменение тестовой учётной записи.
3. Изменение членства в тестовой группе.
4. Запуск программы.
5. Обращение к общему сетевому ресурсу.
6. Выполнение запроса DNS.
7. Получение IP-адреса по DHCP.

Для каждого действия заранее определяется ожидаемый результат журналирования: идентификатор события, время регистрации и необходимые поля записи.

### Порядок измерения для каждой конфигурации

1. **Прогрев (warm-up).** 2 минуты работы в штатном режиме перед замером — для стабилизации ETW, JIT, кэша и фоновых процессов.
2. **Замер «до».** Фиксация свободного места, фактических размеров журналов и значений счётчиков.
3. **Выполнение тестового набора.** Одинаковый для всех конфигураций.
4. **Замер «после».** Повторная фиксация тех же параметров.
5. **Повторение.** Минимум **3 прогона** на конфигурацию для получения статистически значимых значений.

### Метод измерения V (объём данных журналов)

V определяется как разница фактических размеров журналов до и после тестового интервала:

```powershell
$before = (Get-WinEvent -ListLog $LogName).FileSize
# ... тестовые действия ...
$after  = (Get-WinEvent -ListLog $LogName).FileSize
$V = $after - $before
```

Для нескольких журналов значения суммируются. Если журнал перезаписывается и `FileSize` не растёт, используется альтернативный расчёт: `RecordCount × средний размер записи`, где средний размер оценивается по экспорту нескольких событий через `wevtutil epl`.

### Разделение вклада аудита и фона

Для получения **чистого** вклада аудита из измеренных значений вычитается фон:

$$
\Delta U_{аудит} = (U_{нов} - U_{исх}) - \Delta U_{фон}
$$

$$
\Delta S_{аудит} = (S_{своб,0} - S_{своб,1}) - \Delta S_{фон}
$$

Значения $\Delta U_{фон}$ и $\Delta S_{фон}$ берутся из п. 4.3 за тот же интервал.

### Ограничения и пороги значимости

- Если $U_{исх} < 5\%$, значение $\Delta U$ считается **в пределах шума измерения** и не используется как критерий выбора конфигурации. В отчёте это фиксируется отдельно.
- Если фоновое изменение $\Delta S_{фон}$ превышает измеренное $\Delta S_{аудит}$ более чем на порядок, результат признаётся недостоверным и требует увеличения длительности теста.

### Влияние сборщика метрик

Сборщик Data Collector Set **исключается** из измеряемой конфигурации. Все замеры ΔU и ΔS выполняются либо до запуска сборщика, либо при отключённом сборе. Исключение — если целью ставится оценка нагрузки самого сбора данных (тогда это оформляется отдельным экспериментом).

### Измеряемые параметры

- $N$ — количество зарегистрированных событий за измерительный интервал, шт.;
- $T$ — продолжительность измерительного интервала, с;
- $V$ — объём данных, байт;
- $\lambda$ — средняя интенсивность регистрации событий, событий/с;
- $\bar{s}$ — средний размер одной записи, байт/событие;
- $R$ — средняя скорость поступления данных, байт/с;
- $U_{нов}$ — средняя загрузка процессора, %;
- $\Delta U$ — изменение средней загрузки процессора, п.п.;
- $M_{нов}$ — объём используемой оперативной памяти, Мбайт;
- $\Delta M$ — изменение потребления памяти, Мбайт;
- $\Delta S$ — уменьшение свободного дискового пространства, байт.

### Расчётные формулы

$$
\lambda = \frac{N}{T},\quad
\bar{s} = \frac{V}{N},\quad
R = \frac{V}{T} = \lambda \bar{s}
$$

$$
U_{нов}=\frac{1}{m}\sum_{i=1}^{m}u_i,\quad
\Delta U = U_{нов} - U_{исх},\quad
\Delta M = M_{нов} - M_{исх}
$$

### 4.5. Проверка полноты регистрации событий

После завершения тестовых действий необходимо сопоставить ожидаемые события с фактически зарегистрированными записями. Проверяется, оставляет ли каждое тестовое действие необходимые признаки в журналах сервера и клиента.

**Метод:** бинарный чек-лист покрытия. Показатели Precision и Recall **не рассчитываются**, поскольку в двухузловом стенде отсутствует размеченный корпус событий, а правила корреляции (SIEM) не применяются.

Измеряемые параметры:

- $N_{всех\ тестовых}$ — общее количество тестовых сценариев, шт.;
- $N_{обнаруженных}$ — количество сценариев, для которых найдены ожидаемые признаки, шт.;
- $C$ — покрытие тестовых сценариев, %;
- $T_{обн}$ — время обнаружения, с.

Покрытие:

$$
C = \frac{N_{обнаруженных}}{N_{всех\ тестовых}} \cdot 100\%
$$

Время обнаружения:

$$
T_{обн} = t_{сигнал} - t_{действие}
$$

### Правила разметки

| Ситуация | Классификация |
|---|---|
| Ожидаемое событие зафиксировано в течение 60 с после действия | Истинное обнаружение |
| Ожидаемое событие зафиксировано, но без тестового действия (по фоновому интервалу) | Ложное срабатывание |
| Ожидаемое событие не зафиксировано | Пропуск |

Результаты сводятся в таблицу «сценарий → ожидаемый Event ID → обнаружено / не обнаружено → T_обн».

### 4.6. Оценка объёма хранения журналов

На основании измеренной интенсивности регистрации событий и скорости поступления данных определяется суточный объём журналирования и требуемый объём дискового пространства.

Измеряемые и расчётные параметры:

- $V_{сут}$ — расчётный объём данных за сутки, байт;
- $V_{сервер}$, $V_{клиент}$ — суточные объёмы журналирования узлов, байт;
- $V_{\Sigma}$ — суммарный суточный объём, байт;
- $D$ — требуемый срок хранения, суток;
- $K$ — коэффициент запаса;
- $V_{хран}$, $V_{резерв}$ — объёмы за весь срок без запаса и с запасом, байт.

Формулы:

$$
V_{сут} = R \cdot 86400
$$

или, если измерение проведено за $T_{изм,ч}$ часов и получен объём $V_{изм}$:

$$
V_{сут} = V_{изм} \cdot \frac{24}{T_{изм,ч}}
$$

$$
V_{\Sigma} = V_{сервер} + V_{клиент},\quad
V_{хран} = D \cdot V_{\Sigma},\quad
V_{резерв} = K \cdot D \cdot V_{\Sigma}
$$

При плановом запасе 30 % принимается $K = 1{,}3$.

**Допущения.** Измеренный интервал считается репрезентативным для средней суточной нагрузки. Физический объём может отличаться от логического из-за сжатия, индексации и резервного копирования.

### 4.7. Сравнение исследуемых конфигураций

Результаты измерений сводятся в сравнительную таблицу для трёх конфигураций аудита. Сопоставляются: полнота регистрации тестовых событий, суточный объём журналирования, нагрузка на процессор и память, время обнаружения.

Основные показатели сравнения:

- $V_{сут}$ — суточный объём журналирования, байт;
- $\Delta U$ — изменение средней загрузки процессора, п.п.;
- $\Delta M$ — изменение потребления памяти, Мбайт;
- $C$ — покрытие тестовых сценариев, %;
- $T_{обн}$ — время обнаружения, с;
- $T_{рассл}$ — время расследования, с.

**Статистическая значимость.** Сравнение проводится по среднему из **3 повторений**. Если разброс между повторениями превышает 20 % от измеренного значения, конфигурация требует увеличения числа повторений или уточнения метода измерения.

### 4.8. Выбор оптимальной конфигурации

Оптимальной считается конфигурация, обеспечивающая достаточное покрытие заранее определённых угроз при допустимой нагрузке и заданном сроке хранения.

Целевая функция:

$$
J_i = w_C C_i - w_V \frac{V_i}{V_{max}} - w_U \frac{U_i}{U_{max}} - w_F F_i
$$

**Значения весов и порогов для данного стенда:**

| Параметр | Значение | Обоснование |
|---|---|---|
| $w_C$ | 0,5 | Покрытие угроз — приоритет |
| $w_V$ | 0,2 | Хранение важно, но вторично |
| $w_U$ | 0,2 | Нагрузка на CPU и диск |
| $w_F$ | 0,1 | Ложные срабатывания |
| $C_{min}$ | 80 % | Минимально допустимое покрытие |
| $V_{max}$ | 500 МБ/сутки | Ограничение дискового бюджета |
| $U_{max}$ | 5 % | Допустимый прирост загрузки CPU |

**Порядок выбора:**

1. Отсеять конфигурации, не проходящие ограничения: $C \geq C_{min}$, $V \leq V_{max}$, $U \leq U_{max}$.
2. Среди оставшихся выбрать с максимальным $J_i$.
3. Если ни одна не проходит — пересмотреть пороги или доработать конфигурацию.

Малый объём журналов не должен компенсировать отсутствие обнаружения критичной угрозы. Поэтому сначала применяются обязательные ограничения, и только затем — максимизация $J_i$.

### 4.9. Границы методологии

Методика применима при условиях:

- небольшой домен (2 узла, до 10 пользователей);
- слабонагруженный стенд ($U_{исх} < 5\%$);
- Windows Server 2012 R2 и Windows 10 Pro;
- отсутствие SIEM и размеченного корпуса событий.

Методика **не решает**:

- полную верификацию модели угроз (требуется разметка);
- оценку производительности на высоконагруженных системах;
- расчёт Precision и Recall для правил корреляции;
- обнаружение угроз, не оставляющих событий в журналах (rootkit, bootkit, сетевые атаки без логирования).

Методика **даёт**:

- воспроизводимую оценку стоимости каждой конфигурации;
- сравнение по единым метрикам;
- формализованное решение о выборе конфигурации.

Результаты сравнения должны основываться на фактических измерениях. Предположения о том, что максимальная конфигурация обязательно обеспечивает лучшее обнаружение, а сбалансированная — меньшую нагрузку, необходимо проверять экспериментально.

# 5. Сопоставление трёх конфигураций аудита

## 5.1. Конфигурация A — исходная

Сохраняются действующие настройки Windows и существующие журналы без дополнительного расширения аудита.

**Преимущества:**
- минимальное вмешательство в систему;
- сравнительно небольшой объём данных;
- простота получения исходных результатов.

**Недостатки:**
- часть важных событий может не регистрироваться;
- недостаточно подробных сведений для расследования;
- невозможно гарантировать обнаружение изменения политик, запуска вредоносных процессов и доступа к критичным объектам.

**Важно.** Исходная конфигурация должна быть получена **непосредственно с сервера и клиента**. Нельзя заранее утверждать, что аудит отключён или настроен одинаково на обоих узлах. Поскольку часть журналов уже ведётся, все приращения считаются относительно текущего состояния, а не относительно «нуля аудита».

## 5.2. Конфигурация B — максимальная

Включаются все доступные и обоснованные моделью угроз подкатегории аудита, расширенное журналирование процессов, PowerShell, объектов AD, файловой системы, реестра и сетевых служб.

**Преимущества:**
- повышенная полнота данных для расследования;
- подробная регистрация административных действий;
- возможность сопоставлять последовательности событий на сервере и клиенте.

**Недостатки:**
- увеличение объёма журналов;
- рост нагрузки на диск;
- увеличение количества фоновых записей;
- более высокая вероятность ложных срабатываний;
- потенциальная регистрация конфиденциальных данных в командных строках.

Особенно важно учитывать аудит создания процессов (4688). Такая регистрация полезна для расследования, но может раскрывать чувствительные сведения — доступ к журналам должен быть ограничен.

## 5.3. Конфигурация C — сбалансированная

Для небольшого домена предлагается следующая конфигурация:

- успешные и неудачные входы;
- проверка учётных данных;
- изменения пользователей, групп и компьютеров;
- изменения объектов Active Directory;
- изменение политики аудита и параметров безопасности;
- создание процессов;
- журналирование PowerShell;
- события Microsoft Defender;
- контроль создания заданий планировщика и системных служб;
- аудит доступа к критичным файлам и ключам реестра;
- контроль изменений межсетевого экрана;
- журналы DNS, DHCP и RRAS;
- регистрация доступа к SMB, если используется совместный доступ;
- ограниченное журналирование сетевых блокировок;
- контроль очистки журналов и остановки критичных служб.

Не включаются: безусловный аудит всех операций с файлами и реестром, подробное журналирование каждого сетевого пакета и все необязательные подкатегории с высоким потоком событий.

## 5.4. Сравнительная таблица

| Критерий | A — исходная | B — максимальная | C — сбалансированная |
|---|---|---|---|
| Объём данных | Измеряется исходно | Обычно наибольший | Средний, определяется измерением |
| Нагрузка на CPU и диск | Исходный уровень | Потенциально повышенная | Контролируемая |
| Контроль доменных учётных записей | Зависит от настроек | Детальный | Детальный |
| Контроль запуска процессов | Может быть ограничен | Подробный | Включён |
| Контроль PowerShell | Зависит от настроек | Подробный | Включён |
| Контроль файловой системы | Зависит от SACL | Широкий, требует SACL | Выборочный, критичные объекты |
| Контроль DNS, DHCP и RRAS | Зависит от журналов служб | Расширенный | Основные операционные события |
| Расследование изменения политик | Может быть ограничено | Подробное | Обязательные события |
| Вероятность пропуска событий | Потенциально высокая | Потенциально ниже | Низкая для выбранных сценариев |
| Сложность анализа | Низкая при малом объёме | Высокая из-за объёма | Умеренная |
| Применимость | Исходный эксперимент | Верхняя граница нагрузки | Предпочтительный вариант |

Это качественная оценка. Реальные объёмы, задержки и показатели обнаружения должны быть получены экспериментально.

# 7. Практическая реализация сбора и анализа

Для двухузловой инфраструктуры необязательно сразу устанавливать полноценную SIEM. Можно начать со штатного механизма Windows Event Forwarding (WEF), при котором выбранные события с клиента передаются на компьютер-сборщик.

Однако размещение сборщика на том же контроллере домена не обеспечивает независимость хранения: при полной компрометации сервера нарушитель потенциально может воздействовать и на централизованные журналы. В реальной инфраструктуре предпочтителен отдельный защищённый сборщик с ограниченными правами доступа.

Для стенда можно использовать следующую последовательность:

1. Сохранить исходные настройки аудита на сервере и клиенте.
2. Настроить конфигурацию C через отдельные GPO.
3. Выполнить тестовые сценарии и проверить ожидаемые события.
4. Повторить тесты для конфигурации B.
5. Измерить число событий, размер журналов, загрузку CPU и время обнаружения.
6. Сформировать сравнительную таблицу и выбрать конфигурацию по ограничениям и целевой функции.
7. Настроить срок хранения журналов и резервное копирование.

**Сбор метрик perfmon** исключается из измеряемой конфигурации (см. п. 4.4). Если целью ставится оценка нагрузки самого сбора — это оформляется отдельным экспериментом.

# 9. Заключение

Для исследуемой инфраструктуры наиболее критичны угрозы компрометации доменных учётных записей, изменения групповых политик, запуска вредоносных процессов, похищения учётных данных, распространения через SMB и нарушения работы DNS, DHCP и RRAS.

Исходная конфигурация необходима для определения базовой нагрузки, максимальная — для оценки стоимости подробной регистрации, а сбалансированная — для выбора практически применимого набора параметров. Сравнение основывается на измеренном объёме событий, потреблении ресурсов, полноте регистрации тестовых сценариев и времени обнаружения.

Основной ожидаемый результат — не максимальное количество записей в журналах, а **воспроизводимая конфигурация**, которая позволяет обнаруживать заранее определённые угрозы и сохранять достаточно данных для расследования при приемлемых затратах на хранение и обработку.

**Ограничения работы.** Методика измеряет стоимость аудита и покрытие заранее заданных сценариев, но не выполняет полную верификацию модели угроз. Precision и Recall не рассчитываются из-за отсутствия размеченного корпуса. На слабонагруженном стенде значения ΔU могут быть сопоставимы с погрешностью измерения — это фиксируется отдельно. Для практического применения в реальной инфраструктуре требуется масштабирование методики и учёт ограничений Windows Server 2012 R2.
